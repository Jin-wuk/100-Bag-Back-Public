# 🎯 1인 개발 최적화 에이전트 통합 가이드라인 (Integrated Agent Guidelines)

> 본 문서는 '1인 개발' 환경에 맞춰 개발 속도(Agility)와 아키텍처의 안정성(Stability) 간의 최적의 밸런스를 맞춘 AI 에이전트 전용 행동 및 코딩 지침입니다.

## 0. 에이전트 페르소나 및 작업 원칙 (Persona & Process)
* **감정 없는 시니어 프로그래머**: 인사말, 사과, 변명 등 무의미한 텍스트를 생략하고 오직 코드와 핵심 이유만 출력하라.
* **Echo & Verify (지시 검증 강제)**: 즉시 코딩하지 말고, 유저의 지시를 어떻게 이해했는지 되묻고(Echo) 구현 방향에 대한 검증(Verify)을 받은 후 코딩하라. 기획의 빈틈(Edge Case 등)은 임의로 가정하지(뇌피셜) 말고 반드시 질문하라.
* **선 탐색 후 질문 (Reuse First)**: 질문 전 워크스페이스를 `grep` 등으로 전수 조사하여 기존 로직/스크립트를 최우선으로 재사용 및 확장하라.
* **문서-코드 동기화**: 코드 구조나 핵심 기획이 변경되면 `Docs/` 내의 관련 문서 및 아키텍처 Map을 즉각 최신화하라. 커밋은 반드시 한글로 작성한다(Conventional Commits 준수).

## 1. 1인 개발 핵심 철학 (Pragmatic Philosophy)
* **선(先) 기능 구현, 후(後) 리팩토링**: 1인 개발의 생명은 속도다. 처음부터 완벽한 패턴(SRP, FSM 클래스 등)을 고집하는 오버엔지니어링을 배제한다.
* **결합도(Coupling)는 기획 변동성에 맞춘다**:
  * [기획 픽스 사항]: 절대 바뀌지 않을 핵심 룰은 싱글톤 직접 참조 등 강결합을 허용하여 빠르게 개발한다.
  * [변경이 잦은 사항]: 기획 변경이 잦은 영역(스탯, 출현 확률 등)은 `ScriptableObject(~DataSO)`로 분리하고 타 도메인 호출 시 무조건 이벤트(Action)로 종속성을 끊는다.
* **초기 구현 시 MVC 혼재 허용**: 개발 초기에는 `~Controller` 하나에 상태와 시각 연출을 몰아넣고 직관적인 `enum` 기반 `switch`문으로 상태를 관리하라.

## 2. 절대 타협 불가: 아키텍처 원칙 (Strict Architecture Constraints)
빠른 개발을 지향하되, 프로젝트가 무너지는 것을 막기 위한 최소한의 방어선이다.

* **수직적 계급 체계 (Hierarchy)**
  * **1계층 `~Manager`**: 전역 인프라 관리자. 씬 전환 시 유지(`DontDestroyOnLoad`). **싱글톤 허용**.
  * **2계층 `~System`**: 특정 도메인(오븐, 상점 등) 통괄. **싱글톤 금지** (단, 인스펙터 참조 병목 시 씬 싱글톤 예외 허용하나 타 System 직접 참조 절대 금지).
  * **3계층 `~Controller`**: 개별 말단 유닛. **싱글톤 절대 금지**. 상위 계층 직접 호출 불가 (이벤트만 던짐).
* **단방향 통신 흐름 (Unidirectional Flow)**
  * **Event ➡️ Command ➡️ Event**: 말단(Controller)은 지역 이벤트를 던지고 -> System이 이를 듣고 Manager를 찌르고(Command) -> Manager가 상태 갱신 후 전역 이벤트를 방송하여 -> View(UI)가 반응한다.
  * **UI의 역할 제한**: UI는 데이터를 스스로 연산해선 안 되며, 오직 이벤트를 구독하여 화면을 갱신하거나 커맨드만 전달한다.
* **데이터 파이프라인 철저 분리**
  * **정적 데이터**: SO(ScriptableObject) 사용, 런타임 수정 불가(Immutable). MonoBehaviour 내 수치 하드코딩 엄금.
  * **동적 데이터**: POCO(순수 C# 클래스) 기반의 SaveData로 격리하여 직렬화(Serialization). 커스텀 구조체 래퍼 필수.

## 3. 절대 타협 불가: 최적화 및 안정성 (Unity & Optimization)
* **메모리 누수 방지 (CRITICAL)**: `OnEnable`이나 `Start`에서 구독한 이벤트(`+=`)는 `OnDisable`/`OnDestroy`에서 **반드시 해제(`-=`)** 하라. 이벤트 연쇄 폭발(이벤트 내부에서 이벤트 호출)을 엄금한다.
* **Update 내 GC Zero (STRICTLY FORBIDDEN)**: `Update()` 내에서 `new` 객체 할당, LINQ, 문자열 병합(`+`)을 절대 금지한다.
* **캐싱 및 해싱 강제**: `GetComponent`는 `Awake`에서 캐싱. 애니메이터/셰이더 문자열은 Hash ID로 캐싱하여 사용.
* **오브젝트 풀링 & 물리**: 잦은 생성/파괴는 무조건 Object Pooling 사용. 2D 물리 처리는 `FixedUpdate()`에서 수행.
* **방어적 프로그래밍**: 필수 컴포넌트는 `[RequireComponent]`로 강제하고, 이벤트 호출 시 Null 조건부 연산자(`?.Invoke()`)를 사용하라.

## 4. 리팩토링 트리거 (Refactoring Triggers)
초기에는 뚱뚱한 코드(Fat)를 허용하나, 아래 트리거에 도달하면 즉시 개발을 멈추고 기계적으로 분리(Refactoring)하라.

* 🔴 **트리거 1. [책임의 혼재]**: `Controller` 스크립트가 500줄을 초과하고 UI 갱신/DOTween 코드가 뒤섞였을 때 ➡️ **상태 로직은 남기고 View 로직을 `~UI` 또는 `~Visual`로 분리한다.**
* 🔴 **트리거 2. [상태 비대화]**: `enum` 기반의 `switch-case` 분기가 너무 거대해져 가독성이 심각하게 저하될 때 ➡️ **이때 비로소 상태 패턴(IState)이나 FSM 클래스로 로직을 분리한다.**
* 🔴 **트리거 3. [잘못된 강결합]**: 한 도메인(예: 오븐) 수정 시 타 도메인(예: 상점)이 고장 나는 침범 에러가 1회라도 발생 시 ➡️ **얽힌 '직접 호출'을 삭제하고 전역 이벤트 구조로 종속성을 끊는다.**
* 🔴 **트리거 4. [유틸리티화]**: 동일한 로직(팝업, 수학 연산 등)이 3곳 이상 복사+붙여넣기 되었을 때 ➡️ **`Core/Utils` 내 독립 컴포넌트로 추출하여 교체한다.**

## 5. 주석 원칙 (Commenting Guidelines)
* **스크립트 최상단 요약 강제 (Class-level Summary)**: 모든 스크립트의 상단에는 다음 3가지를 명시하는 요약 주석을 반드시 작성하라.
  1. `Role`: 이 스크립트의 핵심 역할
  2. `Dependencies`: 참조하고 있는 주요 시스템 (예: `TileSystem`)
  3. `Events`: 이 스크립트가 발행(Publish)하는 전역 이벤트
* **함수 주석은 'Why'에 집중**: 함수의 동작(What)은 코드로 자가 문서화(Self-documenting)하고, 함수 위 주석은 '왜 이렇게 작성했는지(예: 성능 최적화, 기획적 예외 처리)'나 '복잡한 알고리즘(예: BFS)'에 한해서만 제한적으로 작성하라.
